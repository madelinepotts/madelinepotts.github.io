Project Overview

Fall, 2026 - Present

A GPU-accelerated N-body gravity simulation implemented in CUDA, C++, and OpenGL. The project explores parallel force calculations, numerical integration, interactive visualization, and CUDA performance optimization.

View the project on GitHub

How the Simulation Works

Each simulated body stores a position, velocity, and mass. At every timestep, the program calculates the gravitational acceleration on each body by adding the influence of every other body. This direct approach is intentionally simple and transparent: it has O(N2) cost, but it makes the physics and the effect of each optimization easy to inspect.

The force calculation is distributed across the GPU by assigning one CUDA thread to each target body. The threads process source bodies in shared-memory tiles, allowing all threads in a block to reuse the same source data instead of repeatedly fetching it from slower global memory. This reduces memory traffic while preserving the same physical calculation.

Why Leapfrog Integration

The simulator advances motion with a leapfrog integrator: it first updates velocity by half a timestep, uses that velocity to update position, recalculates the acceleration, and then completes the velocity update. Gravitational systems can accumulate large numerical errors over many steps, so leapfrog is used because it generally preserves long-term energy behavior better than a basic Euler update.

Features

  • Direct O(N2) gravitational force evaluation using the real SI gravitational constant.
  • Leapfrog integration with gravitational softening for improved long-term numerical behavior.
  • Shared-memory float4 force tiles and configurable CUDA threads per block.
  • CUDA/OpenGL vertex-buffer interoperability for direct GPU visualization.
  • GPU-computed energy, momentum, and center-of-mass diagnostics.
  • Interactive playback with pause, single-step, rewind, camera rotation, and zoom controls.

Current Simulation

The default configuration simulates 16,384 bodies for 2,000 steps with a 100-second timestep and 256 CUDA threads per block. The full run represents approximately 55.56 simulated hours.

From Physics to Display

After CUDA calculates a new state, a rendering kernel writes the body positions directly into an OpenGL vertex buffer registered with CUDA. OpenGL then draws those positions as points. This avoids copying every newly calculated frame from the GPU to the CPU and back to the GPU, keeping the simulation and visualization on the device.

The program also tracks total energy, momentum, and center of mass. These diagnostics provide practical checks that the numerical implementation remains physically well behaved while the simulation runs. A CPU-side history stores earlier states so the viewer can pause, step forward, or rewind without rerunning the calculation.

Engineering Decisions

The project deliberately starts with a direct all-pairs solver instead of jumping immediately to a tree algorithm or a more elaborate approximation. That choice keeps the reference calculation easy to reason about and creates a trustworthy baseline for future experiments. Performance changes can be compared against a known physical model rather than against several changing assumptions at once.

The data layout also reflects the calculation. Force evaluation needs position and mass, but not velocity, so the shared-memory tile stores a compact float4 for each source body. At 256 threads per block, that is 4,096 bytes of shared memory for a tile. Small decisions like this make the memory behavior visible and give the project a concrete connection between physics, hardware, and code.

What This Project Explores

This is both a simulation and a laboratory for GPU programming. Changing the number of threads per block makes it possible to compare launch configurations, memory reuse, and timing with CUDA events. The physical diagnostics make performance work more meaningful: a faster kernel is only useful if it still produces a stable and interpretable simulation.

The interactive history controls are intentional as well. They turn a batch calculation into something that can be inspected. Being able to pause on a state, move one step at a time, and rewind makes numerical behavior easier to understand than watching an uninterrupted animation.

Build Requirements

Windows 10 or newer, an NVIDIA GPU with CUDA support, CUDA Toolkit 13.3, CMake 3.18 or newer, Visual Studio 2022 Build Tools, vcpkg, GLFW, GLAD, and OpenGL are required.

Controls

  • Space: play or pause
  • Right Arrow: advance one step
  • Left Arrow: rewind one step
  • Left Mouse + Drag: rotate the camera
  • Mouse Wheel: zoom
  • ESC: exit

Future Directions

Future experiments could compare the tiled direct solver with shared-memory and constant-memory variants, add more initial-condition presets, and investigate larger body counts. A natural longer-term direction would be an approximate method such as a Barnes-Hut tree, with the direct solver retained as a validation reference. The current architecture is meant to make those comparisons possible without hiding the underlying physics.
